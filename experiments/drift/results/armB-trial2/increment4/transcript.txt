## What I added

**`prisma/schema.prisma`** — on `InventoryDaily`, replaced the standalone `@@index([productId])` with a composite `@@index([productId, snapshotDate])`. This is the access path the new page needs (filter by product, group/order by date), and because `productId` is the leftmost column it still serves every query the old single-column index did, so nothing regresses.

**`src/queries.ts`** — a new "Page 8" following the existing structure (typed row interface + async function, same `groupBy`/aggregate style as Page 4's regional summary):

```ts
export interface ProductCostTrendRow {
  snapshotDate: Date;
  avgCostPerUnit: number;
}

export async function getProductCostTrend(productId: number): Promise<ProductCostTrendRow[]>
```

It groups `InventoryDaily` by `snapshotDate` for the given product, averages `costPerUnit` (that's the "combined across every store" — the mean per-unit cost across all stocking stores on each date), and orders ascending by date in the DB.

One interpretation call worth flagging: **"combined across every store" I read as the average per-unit cost across stores per date.** That's the natural read for a cost-over-time trend line and I noted it in the doc comment. If the analyst actually wants a different combine (e.g. an inventory-value-weighted average, or min/max band), it's a one-line change to the aggregate — say the word.

Note the schema index is a design change to `schema.prisma`; it won't hit the actual `dev.db` until a `prisma migrate`/`db push` is run, which I did not do since this run directory looks like part of an experiment harness. The query itself is correct regardless of the index.
